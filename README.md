# 警报处理系统双流验证方案

## 1. 方案概述

### 1.1 背景说明
- **老系统**: C# + TIBCO + Oracle + 生产环境运行
- **新系统**: Java(Spring Boot) + RabbitMQ + Vastbase + 容器云 + Redis + Prometheus + Grafana
- **验证目标**: 在不影响生产业务的前提下,验证新系统功能正确性和性能可靠性

### 1.2 验证策略
采用**双流双出**并行验证方案,通过同时处理相同警报消息,对比新老系统处理结果,识别差异并持续优化。

## 2. 整体架构设计

### 2.1 系统部署架构

```
                    ┌─────────────────┐
                    │  上游警报系统    │
                    └────────┬────────┘
                             │
                             ▼
                    ┌─────────────────┐
                    │  TIBCO 消息总线  │
                    └────┬──────┬─────┘
                         │      │
              原有路径 ──┘      └── 新增转发路径
                         │              │
                         ▼              ▼
           ┌──────────────────┐  ┌──────────────────┐
           │   老系统(C#)      │  │  新系统(Java)     │
           │   - TIBCO接收     │  │  - RabbitMQ接收   │
           │   - Oracle存储    │  │  - Vastbase存储   │
           │   - 通知&动作     │  │  - 通知&动作      │
           └─────────┬────────┘  └─────────┬─────────┘
                     │                     │
                     ▼                     ▼
           ┌──────────────────┐  ┌──────────────────┐
           │   Oracle DB       │  │   Vastbase DB     │
           └─────────┬────────┘  └─────────┬─────────┘
                     │                     │
                     └──────────┬──────────┘
                                │
                                ▼
                   ┌─────────────────────────┐
                   │  数据同步 & 对比验证程序  │
                   │  - 实时数据同步          │
                   │  - 结果差异对比          │
                   │  - 差异分析报告          │
                   └─────────────────────────┘
```

### 2.2 核心组件说明

| 组件 | 职责 | 关键点 |
|------|------|--------|
| **TIBCO消息转发器** | 将警报消息同时发送给老系统和RabbitMQ | 消息双写、保证消息一致性 |
| **新系统接收模块** | 从RabbitMQ消费警报消息 | 消费确认机制、重试策略 |
| **数据同步程序** | 实时同步老系统Oracle数据到Vastbase | 双向同步、冲突检测 |
| **结果对比程序** | 对比新老系统处理结果 | 差异识别、根因分析 |
| **监控告警系统** | Prometheus + Grafana监控新系统 | 实时监控、异常告警 |

## 3. 关键验证维度

### 3.1 功能正确性验证

#### 3.1.1 消息处理准确性
- **验证目标**: 新系统能够正确解析和处理所有类型的警报消息
- **验证方法**:
  1. 消息接收完整性检查
     - 对比新老系统接收到的消息数量
     - 检查消息内容是否完全一致(MD5/SHA256校验)
  
  2. 消息解析准确性检查
     - 提取关键字段进行逐字段对比
     - 特殊字符、空值、边界值处理验证
  
  3. 消息处理逻辑验证
     - 警报分类准确性
     - 优先级判定准确性
     - 状态转换逻辑一致性

- **验证标准**:
  - 消息接收率 ≥ 99.99%
  - 字段解析准确率 = 100%
  - 逻辑处理一致率 ≥ 99.9%

#### 3.1.2 数据入库一致性
- **验证目标**: 新系统存储的数据与老系统完全一致
- **验证方法**:
  1. 表结构验证
     - 确认Vastbase与Oracle表结构完全对应
     - 字段类型、长度、约束一致性检查
  
  2. 数据完整性验证
     - 按时间段对比记录总数
     - 关键字段(警报ID、时间戳、状态等)逐条对比
  
  3. 数据准确性验证
     - 抽样对比详细记录内容
     - 计算字段、关联字段准确性验证
     - 时间戳精度验证(考虑时区差异)

- **验证工具**:
  - 自动化对比脚本(SQL对比查询)
  - 数据差异报告生成器
  - 可视化差异展示工具

- **验证标准**:
  - 数据完整率 = 100%
  - 数据准确率 = 100%
  - 允许时间戳误差 < 1秒

#### 3.1.3 规则引擎验证
- **验证目标**: 新系统的警报规则匹配和执行与老系统一致
- **验证方法**:
  1. 规则配置迁移验证
     - 对比新老系统规则配置完整性
     - 规则语法转换正确性验证
  
  2. 规则匹配准确性
     - 相同警报触发相同规则
     - 规则优先级处理一致
     - 组合条件判断准确
  
  3. 规则执行结果验证
     - 通知对象准确性
     - 通知内容一致性
     - 动作执行参数正确性

- **验证标准**:
  - 规则匹配准确率 = 100%
  - 通知对象准确率 = 100%
  - 动作参数准确率 = 100%

#### 3.1.4 通知功能验证
- **验证目标**: 验证新系统通知功能的准确性和及时性
- **验证方法**:
  1. 通知对象准确性
     - 对比通知接收人列表
     - 验证角色/权限映射正确性
  
  2. 通知内容准确性
     - 通知模板渲染正确性
     - 动态内容填充准确性
     - 多语言支持验证(如适用)
  
  3. 通知渠道验证
     - 邮件、短信、IM等多渠道验证
     - 渠道降级策略验证
  
  4. 通知时效性
     - 从警报接收到发送通知的时延
     - 对比新老系统时延差异

- **验证标准**:
  - 通知对象准确率 = 100%
  - 通知内容准确率 = 100%
  - 时延差异 < 2秒

### 3.2 性能可靠性验证

#### 3.2.1 吞吐量验证
- **验证目标**: 新系统能够处理预期的消息负载
- **验证方法**:
  1. 基线性能测试
     - 测试不同消息速率下的处理能力
     - 记录CPU、内存、网络IO等资源使用情况
  
  2. 峰值压力测试
     - 模拟历史最大消息峰值(如去年最高峰值的1.5倍)
     - 验证系统是否能够稳定处理
  
  3. 持续负载测试
     - 连续24小时平均负载测试
     - 观察性能衰减情况

- **性能指标**:
  - 目标TPS: ≥ 老系统峰值 × 1.2
  - 单条消息处理时延: < 500ms (P99)
  - CPU使用率: < 70% (峰值)
  - 内存使用: < 80% (峰值)

#### 3.2.2 响应时延验证
- **验证目标**: 确保新系统响应速度不低于老系统
- **验证方法**:
  1. 端到端时延测试
     - 从消息到达到处理完成的总时延
     - 分段时延分析(接收→解析→处理→存储→通知)
  
  2. 时延分布分析
     - P50、P95、P99、P999时延
     - 长尾时延根因分析
  
  3. 对比分析
     - 新老系统同一时间段时延对比
     - 识别性能瓶颈环节

- **性能标准**:
  - P99时延 ≤ 老系统P99 × 1.1
  - 平均时延 ≤ 老系统平均时延

#### 3.2.3 稳定性验证
- **验证目标**: 新系统能够长期稳定运行
- **验证方法**:
  1. 长时间运行测试
     - 7×24小时连续运行测试
     - 监控系统资源泄漏(内存、连接数、文件句柄等)
  
  2. 异常场景测试
     - 数据库连接中断恢复
     - RabbitMQ连接中断恢复
     - Redis连接中断恢复
     - 网络波动场景测试
  
  3. 故障注入测试
     - 模拟组件故障(Chaos Engineering)
     - 验证降级策略和容错机制
     - 测试故障恢复时间

- **稳定性标准**:
  - 系统可用性 ≥ 99.9%
  - 故障自动恢复时间 < 5分钟
  - 无内存泄漏、连接泄漏

#### 3.2.4 容量规划验证
- **验证目标**: 验证系统容量规划的合理性
- **验证方法**:
  1. 资源使用基线
     - 不同负载下的资源使用曲线
     - 容器资源配额合理性验证
  
  2. 扩容能力验证
     - 水平扩容效果测试
     - 验证负载均衡效果
  
  3. 存储容量评估
     - 数据增长速率统计
     - 存储容量预测和规划

- **容量标准**:
  - 支持未来6个月业务增长
  - 扩容后性能线性提升

### 3.3 可用性验证

#### 3.3.1 高可用架构验证
- **验证目标**: 验证系统高可用设计的有效性
- **验证方法**:
  1. 组件冗余验证
     - 应用多实例部署验证
     - RabbitMQ集群验证
     - Redis主从/哨兵验证
     - 数据库主从切换验证
  
  2. 故障切换验证
     - 主节点故障自动切换
     - 切换时间和数据丢失情况
     - 切换对业务的影响

- **可用性标准**:
  - RTO(恢复时间目标) < 5分钟

#### 3.3.2 监控告警验证
- **验证目标**: 确保监控系统能够及时发现问题
- **验证方法**:
  1. 监控指标覆盖度
     - 应用层指标(QPS、时延、错误率)
     - 系统层指标(CPU、内存、磁盘、网络)
     - 业务层指标(消息积压、处理成功率)
  
  2. 告警规则验证
     - 触发告警阈值合理性
     - 告警通知及时性(< 1分钟)
     - 告警分级和升级机制
  
  3. 可视化验证
     - Grafana仪表盘完整性
     - 关键指标可视化效果

- **监控标准**:
  - 核心指标监控覆盖率 = 100%
  - 告警准确率 ≥ 95%(减少误报)
  - 告警响应时间 < 1分钟

#### 3.3.3 运维能力验证
- **验证目标**: 验证系统可运维性
- **验证方法**:
  1. 日志完整性验证
     - 关键操作日志记录
     - 日志格式标准化
     - 日志检索能力(ELK/日志平台)
  
  2. 问题诊断能力
     - 通过日志定位问题
     - 通过监控定位性能瓶颈
     - 链路追踪能力(如适用)
  
  3. 运维操作验证
     - 配置热更新
     - 灰度发布流程
     - 回滚操作验证

## 5. 动作执行验证策略

### 5.1 分阶段动作验证

由于动作执行可能对业务产生影响,采用更加谨慎的验证策略:

#### 阶段1: 动作Mock验证 (第6周)
- 新系统仅记录动作执行日志,不实际执行
- 对比新老系统的动作执行决策
- 验证动作参数准确性
- 目标: 动作决策准确率 = 100%

#### 阶段2: 幂等动作验证 (第7周)
- 选择幂等动作(重复执行无副作用)
- 新老系统同时执行,对比结果
- 监控业务影响
- 目标: 无业务投诉

#### 阶段3: 重要动作验证 (第8周)
- 选择1-2个低风险的重要动作
- 与业务方协商验证窗口
- 准备回滚预案
- 实时监控业务指标
- 目标: 业务指标正常

#### 阶段4: 全量动作验证 (第9周)
- 逐步放开所有动作执行
- 严格监控业务影响
- 建立快速回滚机制
- 目标: 所有动作验证通过

### 5.2 动作执行风险控制

1. **动作分类管理**
   - 幂等动作: 可重复执行,优先验证
   - 非幂等动作: 需要去重机制
   - 高风险动作: 需要业务方确认

2. **去重机制**
   - 基于警报ID+动作类型的去重
   - Redis分布式锁防止并发执行
   - 去重记录有效期24小时

3. **回滚预案**
   - 动作执行记录完整
   - 支持手动回滚操作
   - 建立补偿机制

## 6. 数据对比验证方案

### 6.1 实时对比程序设计

#### 6.1.1 消息级对比
```sql
-- 每分钟统计对比
SELECT 
    DATE_FORMAT(receive_time, '%Y-%m-%d %H:%i') as time_window,
    COUNT(*) as total_count,
    system_source
FROM alert_messages
WHERE receive_time >= DATE_SUB(NOW(), INTERVAL 5 MINUTE)
GROUP BY time_window, system_source;
```

#### 6.1.2 数据级对比
```sql
-- 关键字段对比(每小时执行)
SELECT 
    a.alert_id,
    a.alert_type as old_type, b.alert_type as new_type,
    a.priority as old_priority, b.priority as new_priority,
    a.status as old_status, b.status as new_status,
    a.handler as old_handler, b.handler as new_handler
FROM oracle_db.alert_records a
LEFT JOIN vastbase_db.alert_records b ON a.alert_id = b.alert_id
WHERE a.alert_type != b.alert_type 
   OR a.priority != b.priority
   OR a.status != b.status
   OR a.handler != b.handler
   OR b.alert_id IS NULL;
```

#### 6.1.3 规则执行对比
```sql
-- 规则触发对比
SELECT 
    a.alert_id,
    a.matched_rules as old_rules,
    b.matched_rules as new_rules,
    a.notify_users as old_users,
    b.notify_users as new_users
FROM oracle_db.rule_execution_log a
LEFT JOIN vastbase_db.rule_execution_log b ON a.alert_id = b.alert_id
WHERE a.matched_rules != b.matched_rules 
   OR a.notify_users != b.notify_users;
```

|---------|---------|---------|---------|---------|

| | 数据库性能瓶颈 | 中 | 中 | 索引优化,读写分离,连接池调优 |
| | 消息队列积压 | 中 | 中 | 增加消费者,优化处理逻辑 |

| | 第三方依赖不稳定 | 中 | 中 | 实现降级策略,异常重试机制 |

| | 故障响应不及时 | 中 | 中 | 完善监控告警,建立应急响应流程 |

### 8.2 应对措施

#### 8.2.1 快速回滚机制
- **场景1: 新系统重大Bug**
  - 立即停止消息转发到新系统
  - 老系统继续处理,业务不受影响
  - 回滚时间 < 5分钟

- **场景2: 性能严重不足**
  - 限流保护,防止雪崩
  - 扩容资源(水平扩展)
  - 优化代码热更新

- **场景3: 数据不一致**
  - 暂停新系统写入
  - 分析根因
  - 数据修复后恢复

#### 8.2.2 限流保护
- 在新系统入口处实施限流
- 基于Guava RateLimiter或Sentinel
- 初始限流值设置为老系统峰值的1.2倍
- 超过限流直接丢弃,记录告警

#### 8.2.3 降级策略
- **级别1: 缓存降级**
  - Redis故障时,降级为本地缓存
  - 牺牲一致性,保证可用性

- **级别2: 功能降级**
  - 非核心功能关闭(如统计、日志上报)
  - 保证核心功能正常

- **级别3: 读写降级**
  - 只读模式,停止写入
  - 等待故障恢复

#### 8.2.4 应急响应流程
```
故障发生 → 监控告警 → 值班人员确认(5分钟内)
    → 判断严重程度
        → P0: 立即拉群,通知Leader,启动应急预案
        → P1: 值班人员处理,必要时升级
        → P2: 记录问题,正常时间处理
    → 问题定位(查看日志、监控、链路追踪)
    → 快速修复或回滚
    → 验证恢复
    → 事后复盘
```

### 9.2 同步方案选型

#### 方案1: 基于CDC的实时同步(推荐)
- **实现方式**: 使用Debezium + Kafka
- **优点**:
  - 实时性高(秒级延迟)
  - 对源库影响小
  - 支持断点续传
  - 可审计、可回溯
- **缺点**:
  - 架构复杂
  - 需要额外的Kafka集群
- **适用场景**: 对实时性要求高,数据量大

#### 方案2: 基于触发器的实时同步
- **实现方式**: 在Oracle上创建触发器,写入同步队列
- **优点**:
  - 实时性高
  - 实现简单
- **缺点**:
  - 对源库性能影响大
  - 触发器管理复杂
  - 容易出现死锁
- **适用场景**: 数据量小,表数量少

#### 方案3: 定时增量同步
- **实现方式**: 根据时间戳定时同步增量数据
- **优点**:
  - 实现简单
  - 对源库影响可控
- **缺点**:
  - 实时性差(分钟级)
  - 依赖时间戳字段
  - 无法捕获删除操作
- **适用场景**: 对实时性要求不高

```java
// Oracle → Vastbase 数据类型转换
public class DataTypeConverter {
    public static Object convertOracleToVastbase(Object value, String oracleType) {
        switch (oracleType) {
            case "NUMBER":
                // Oracle NUMBER → Vastbase NUMERIC
                return new BigDecimal(value.toString());
            case "DATE":
                // Oracle DATE → Vastbase TIMESTAMP
                return Timestamp.from(((Date) value).toInstant());
            case "CLOB":
                // Oracle CLOB → Vastbase TEXT
                return readClob((Clob) value);
            // ... 其他类型转换
            default:
                return value;
        }
    }
}
```

#### 9.3.4 冲突检测策略
```java
// 检测新老系统同时写入造成的冲突
public class ConflictDetector {
    public ConflictResolution detectConflict(Record oldRecord, Record newRecord) {
        // 1. 基于时间戳判断
        if (oldRecord.getUpdateTime().isAfter(newRecord.getUpdateTime())) {
            return ConflictResolution.USE_OLD;
        }
        
        // 2. 基于版本号判断
        if (oldRecord.getVersion() > newRecord.getVersion()) {
            return ConflictResolution.USE_OLD;
        }
        
        // 3. 基于来源优先级(验证期间老系统优先)
        if (oldRecord.getSource() == Source.OLD_SYSTEM) {
            return ConflictResolution.USE_OLD;
        }
        
        return ConflictResolution.USE_NEW;
    }
}
```

- [ ] 实时监控新系统运行状态
- [ ] 持续2小时,无异常则扩大范围

#### 阶段3: 全量切换 (T+2小时)
- [ ] 所有上游系统切换到新系统
- [ ] 老系统切换为只读模式
- [ ] 持续监控24小时

#### 阶段4: 老系统下线 (T+7天)
- [ ] 新系统稳定运行7天
- [ ] 数据完整性最终确认
- [ ] 老系统数据归档
- [ ] 老系统资源释放

### 10.3 回滚预案

#### 回滚触发条件(任一满足即回滚)
- 新系统处理成功率 < 99%,持续10分钟
- 出现数据丢失或严重错误
- 消息积压持续增长,超过10000
- P0故障无法在30分钟内修复

#### 回滚步骤
1. 停止上游系统向新系统发送消息(5分钟内)
2. 恢复老系统为主系统(10分钟内)
3. 新系统切换为只读模式
4. 数据补偿(处理回滚期间的消息)
5. 问题分析和修复
